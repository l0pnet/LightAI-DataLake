# LightAI-DataLake（轻量 AI 数据湖）系统需求文档

## 1. 系统概述
### 1.1 产品定位
LightAI-DataLake 是一款面向 AI 开发者的轻量级数据基础设施，通过“元数据驱动 + 工具链集成 + CLI 交互”的创新模式，实现数据全生命周期管理。该系统旨在替代传统重型数据中台，为中小型企业、科研机构及创业团队提供低成本、高灵活性的数据解决方案。

### 1.2 目标与范围
- 目标：为 AI 开发者提供开箱即用的数据管理能力，降低数据基础设施的维护成本，提升研发效率。
- 范围：覆盖数据入湖、元数据管理、计算处理、运维监控等环节，支持从数据导入到分析的全流程。系统设计为通用型，可适配不同行业场景，如 IoT、金融或医疗。

### 1.3 目标用户
- 有一定基础的 IT 人员、AI 工程师或大数据分析师，熟悉 Python、Shell 及命令行操作。
- 用户通过自然语言提示词驱动系统，无需深度了解底层技术细节。

### 1.4 目标市场和场景
- 制造业：设备传感器数据监控与预测性维护
- 金融科技：交易数据实时分析与风险监控
- 医疗健康：医疗影像数据管理与分析研究
- 能源管理：储能设备监控与能源调度优化
- 零售电商：用户行为分析与个性化推荐
- 智慧城市：城市基础设施监控与智能调度

## 2. 功能需求
### 2.1 数据存储架构
#### 2.1.1 多模态存储支持
- 时序数据存储：集成 TDEngine，专为物联网传感器数据优化，支持高速写入和查询
- 关系型数据存储：PostgreSQL 作为核心结构化数据引擎，支持复杂查询和事务
- 文档型数据存储：MongoDB，支持半结构化数据和灵活 schema
- 非结构化数据存储：基于 MinIO 或类似技术的对象存储，支持文档、图像、视频等
- 缓存层：Redis 集群，提供热点数据缓存和会话管理

#### 2.1.2 容量规划
| 数据类型       | 日增量容量 | 存储周期 | 总容量估算 | 缓存需求               |
|----------------|------------|----------|------------|------------------------|
| 实时时序数据   | 200GB/天   |          | ~219TB     | 热点数据缓存           |
| 结构化数据     | 10GB/天    | 3年      | ~11TB      | 查询结果缓存           |
| 文档型数据     | 20GB/天    |          | ~22TB      | 索引和元数据缓存       |
| 非结构化数据   | 50GB/天    | 3年      | ~55TB      | 元数据缓存             |

#### 2.1.3 Redis 缓存层功能
- 查询缓存：缓存频繁查询结果，提升数据访问性能
- 会话管理：用户会话和临时状态存储
- 消息队列：支持轻量级消息队列功能，用于任务调度
- 分布式锁：支持分布式环境下的资源锁管理

### 2.2 元数据驱动架构
#### 2.2.1 元数据管理
元数据仓库结构：
```plaintext
├── datasources/ # 数据源定义
├── pipelines/ # 数据处理流水线
├── schemas/ # 数据模式定义
├── quality/ # 数据质量规则
├── lineage/ # 数据血缘关系
├── skills/ # 技能定义
```

#### 2.2.2 Git 版本管理
- 所有元数据文件采用 Markdown 格式，便于人工阅读和机器解析
- 支持分支管理，实现元数据变更的协作开发
- 自动化的元数据校验和冲突解决机制

### 2.3 数据接入与同步
#### 2.3.1 历史数据导入
- 批量导入工具：支持从外部数据源（如关系数据库、文件系统、对象存储）批量导入历史数据
- 数据迁移框架：提供可配置的数据迁移流水线，支持数据转换和清洗
- 进度监控：实时监控导入进度，支持断点续传和错误重试
- 一致性保证：确保历史数据导入的完整性和一致性

#### 2.3.2 增量数据同步
- 变更数据捕获（CDC）：支持基于日志的实时数据变更捕获
- 增量同步机制：自动识别和处理增量数据，避免全量同步
- 多源同步：支持从多个数据源并发同步数据
- 数据一致性：保证增量同步过程中的数据最终一致性

#### 2.3.3 数据源支持
- 时序数据库：TDEngine、InfluxDB、TimescaleDB 等
- 关系数据库：MySQL、Oracle、SQL Server、PostgreSQL 等
- NoSQL 数据库：MongoDB、Cassandra、Redis、Elasticsearch 等
- 文件数据源：CSV、JSON、Parquet、ORC 等格式文件
- 消息队列：Kafka、RabbitMQ 等消息中间件
- 云存储：AWS S3、Azure Blob Storage 等

### 2.4 数据操作功能
#### 2.4.1 计算引擎
- 批处理计算：集成 Spark 或 Dask，支持大规模数据离线处理
- 流式计算：集成 Flink 或类似引擎，支持实时数据计算
- 交互式查询：支持即席查询和探索性数据分析

#### 2.4.2 数据治理
- 数据清洗：支持数据去重、格式标准化、异常值处理
- 质量检查：内置数据质量规则引擎，支持自定义质量规则
- 血缘追踪：完整的数据血缘关系追踪和分析

## 4. 系统架构
### 4.1 整体架构图
```plaintext
客户端工具层        监控看板        元数据 Git
CLI+Skills        (Grafana)      (Markdown)
        ￬
数据接入与同步层
| + 历史数据导入 + 增量同步 + 数据质量检查

缓存层        计算引擎层        数据治理层
| - Redis集群   批处理          数据质量
  本地缓存     流处理          数据血缘
        ￬
多模数据存储层
| + TDEngine + PostgreSQL + MongoDB + MinIO + ...

容器编排层        调度引擎层        监控告警层
Kubernetes        Rundeck          Prometheus
```

### 4.2 数据接入架构
#### 4.2.1 历史数据导入流程
```plaintext

```

#### 4.2.2 增量同步架构
- CDC 采集：基于数据库日志的实时变更捕获
- 消息队列：变更事件通过消息队列异步处理
- 数据转换：实时数据清洗和格式标准化
- 异常处理：同步失败自动重试和告警

### 4.3 缓存架构设计
#### 4.3.1 Redis 集群配置
- 主从复制：保证数据高可用
- 分片存储：支持数据水平分片，提升容量和性能
- 持久化策略：RDB + AOF 混合持久化，平衡性能与可靠性

#### 4.3.2 缓存应用场景
- 查询结果缓存：复杂查询结果缓存，设置合理 TTL
- 同步状态缓存：数据同步任务状态和进度缓存
- 元数据缓存：频繁访问的元数据信息缓存

### 4.4 容器化架构
#### 4.4.1 Kubernetes 集群
- 节点管理：自动化的节点发现和集群管理
- 服务发现：基于 DNS 的服务发现和负载均衡
- 存储编排：动态存储卷供给和管理
- 自动部署：支持蓝绿部署和滚动更新

#### 4.4.2 容器编排策略
- 资源调度：基于资源需求的智能容器调度
- 弹性伸缩：根据负载自动扩展或收缩容器实例
